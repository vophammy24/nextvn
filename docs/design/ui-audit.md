# NextVN UI audit — Phase A

Audit date: 2026-10-14 (Asia/Saigon). Branch: `develop`.

Status: source audit completed; baseline browser evidence and validation are summarized in [ui-improvement-report.md](ui-improvement-report.md). This is the audit phase, not a completed redesign. No application, backend, database, authentication, calculation, or permission code was changed.

## Scope and evidence

The route source of truth is `client/src/App.tsx`, not the directory names or `app/navigation.ts`. There are **20 rendered pages**: 3 public, 4 shared sales pages, 4 Manager inventory pages, and 9 Owner pages. There are also 2 Owner redirect aliases, the `/app` layout entry, and a wildcard redirect. Admin has no implemented frontend routes. All nonempty page implementations, their shared components, role boundaries, stylesheets, and existing client tests were inspected. No `AGENTS.md` was found in the workspace ancestry or project scan.

Browser baseline uses synthetic responses intercepted in a separate browser context, with external requests blocked. These are UI fixtures, not application/demo dataset changes. The full 20-page matrix uses widths 1920, 1366, 1024, 768, 390, and 360. Source findings below are distinguished from measured browser results. Screenshots represent baseline behavior only; there are no after screenshots because implementation has not begun. Populated sales/inventory examples and predominantly empty Owner datasets do not establish production-data or every-state coverage.

## Actual architecture

- React 19, TypeScript, Vite; React Router; TanStack Query for server state; Zustand cart; Axios; Zod; Lucide icons; Recharts.
- `main.tsx` mounts BrowserRouter and QueryClientProvider and imports `index.css`. `App.css` is a comment-only file.
- `ProtectedApplication` checks token presence and wraps **all authenticated pages in StaffLayout**, through WorkspaceProvider. StaffLayout is therefore the actual shared shell despite its name.
- `WorkspaceProvider` supplies verified business/branch/role context. The workspace schema admits STAFF, MANAGER, and OWNER. InventoryRoute and OwnerRoute enforce their existing role conditions. Sales services require a Staff/Manager branch scope; sales route elements do not contain equivalent UI role guards. Preserve this behavior during styling and document any permission changes separately.
- Staff pages contain their own header, controls, status rendering, and dialogs. The named POS/table component files are empty placeholders.
- Manager inventory uses InventoryRoute → ManagerPage → InventoryDataBoundary → existing features. Dashboard, Reports, and Staff feature implementations exist but are not registered in App; their development boundary is explicitly illustrative.
- Eight Owner pages are branches of `OwnerWorkspace.tsx`; inventory overview is separate and uses Manager/Foundation styles. Owner route changes remount the workspace by business ID and pathname.
- Existing shared code worth retaining: Foundation PageHeader, SectionCard, ChartCard, StatCard, feedback states, StatusBadge, RoleBadge, Avatar, SearchInput, FilterTabs; generic DataTable; AnalyticsChart; AuthCard; Vietnamese formatting helpers.

## Route inventory

Risk means risk **of the proposed later refactor**, not a claim of an existing business defect. Low = presentation-only; medium = state/keyboard/form lifecycle; high = adjacent to payment, permissions, or inventory payloads. For each shared sales page, Staff and Manager are the intended business roles and currently see its shell link. Manager also sees Shift despite navigation metadata specifying Staff only. Owner can address sales URLs directly, but the sales service rejects its scope; do not silently change that access behavior.

## Cross-cutting findings

1. **High — dialogs and narrow overflow.** `.modal-content` has `min-width: 400px`; mobile CSS targets `.modal`, which these dialogs do not use. Both sales dialogs lack role/name/modal semantics, Escape handling, initial/return focus and containment. `.card:has(> .data-table)` does not match nested Orders/Shift tables.
2. **High — route metadata is not the live menu.** Existing typed icons are available, but Owner shell hardcodes LayoutGrid for every destination. Metadata also includes unavailable routes and a Manager home pointing to `/app/dashboard`, whereas login correctly redirects Manager to inventory. Refactor the live menu with an explicit whitelist of currently visible destinations; preserve redirects and permissions.
3. **High — competing themes.** Global primary is `#6366f1`; landing uses `#4f46e5` and a lavender yellow token; Owner uses `#176b5b`. Owner inventory switches back to global purple. Keep white readable surfaces; use a blue/navy shell and limited yellow accents across all pages together in the foundation phase.
4. **High — keyboard/labels.** Product/table card Space activation is absent. Orders filters and eye buttons need accessible names. New-member role needs a label. Revenue tabs do not implement the semantics they claim. StaffLayout lacks a skip link and Escape menu closing; its in-flow mobile disclosure does not need a modal focus trap unless redesigned as an overlay drawer.
5. **Medium — typography/contrast.** Inter exists globally; Owner uses another body family plus serif titles. Manager often uses 10–12px supporting text. Global tertiary `#94a3b8` on white is unsuitable for normal text contrast. Validate actual computed pairs during implementation; this audit does not claim WCAG conformance.
6. **Medium — feedback.** Foundation already provides accessible LoadingState/ErrorState/EmptyState. Staff duplicates unannounced loading/error blocks and native alerts. Owner loading lacks `role=status`; some raw Owner tables have no empty message. Staff shift history/summary and order detail need dedicated error presentation. Table bill fetch failures are currently indistinguishable from no bill; changing that state lifecycle needs targeted tests.
7. **Medium — business/branch context.** Owner shows business context in its heading. Staff/Manager shell lacks a consistent context/header/profile area. Display already available context only; do not implement unsupported business selection or notifications.
8. **Medium — repeated values and incomplete primitives.** `.btn`, `.button`, `.lp-button`, manager fields and Owner fields diverge. Hardcoded shadows, font sizes, colors and padding repeat across six CSS files. Consolidate aliases before replacing call sites to avoid a staggered mixed theme.
9. **Medium — browser branding.** `index.html` has `lang=en`, title `client`, and a template favicon. Auth/shell show a Coffee icon; public uses `nextvn.`. Active source search found no Nezt/Veaen labels, but NextVN capitalization is inconsistent. Use `lang=vi`, consistent title and a documented authentic mark strategy later.
10. **Medium — motion/touch.** Reduced motion exists for landing and Owner, but global treatment only disables spinner animation; hover translations and modal animations remain. POS quantity controls are only 28px. Target at least 44px for frequent touch actions without claiming every 28px target automatically violates WCAG.
11. **Low — legacy CSS and bundle size.** Owner retains unused sidebar/topbar selectors and later override rules. Build bundles the app into a ~970 kB JS chunk before gzip. Cleanup and route splitting are later work, not required to change business behavior.

## Brand reference

The existing `docs/design/nextvn-brand-reference.pdf` is approximately 97 MB and has seven page objects. Embedded image objects 29 and 411 were extracted and visually inspected: the former contains the authentic stylized white/cyan N on blue with a yellow circular detail and the old **NEZT VEAEN** lockup; the latter contains an old white wordmark. These are raster PDF image assets, not an approved NextVN vector logo. A full rendered page-by-page PDF inspection was not available in this environment; exact color specifications have not been verified.

Do not ship the old wordmark or invent an official replacement symbol. Future implementation should reuse a verified symbol extraction with correct proportions and separate NextVN text, or use a clearly documented text-only interim lockup until authentic vector artwork is available. The user-proposed palette remains a starting specification, not a PDF color measurement.

| landing.css               | 1100, 920, 640                 | Separate public nav and section breakpoints                                                |
| auth.css                  | 480                            | Reduced card/page padding                                                                  |
| inventory/integration.css | No media queries               | Depends on global and Manager breakpoints; tables have local scrolling                     |

Keep the existing breakpoints until measured content pressure warrants changing them. Use local table overflow, minmax(0,1fr), wrapping headings/actions and viewport-bounded dialogs. Test 768 and 1024 explicitly: the desktop sidebar persists there. Ensure POS product browsing and checkout remain reachable when stacked, including a long cart and on-screen keyboard.

## Implementation sequence and regression gates

Phase B: semantic token consolidation across all six CSS layers, one font scale, brand lockup, reusable button/input/notice/dialog primitives where actually used. Phase C: live-menu icon mapping, context/header consistency and mobile disclosure behavior. Phase D: Staff, Manager and Owner route interactions; no Admin implementation. Phase E: landing/auth polish, preserving public routes and Google unavailability. Phase F: keyboard, screen reader, zoom, reduced motion and narrow state coverage. Phase G: regression/build plus before/after captures.

Prioritize meaningful tests for native product activation, dialog focus/Escape/return, menu visibility and current links, unchanged checkout payload, recipe/transaction payloads, and unchanged auth redirects. Preserve all existing tests. Do not create tests that merely assert chosen CSS values. Full acceptance additionally requires populated charts, long Vietnamese text, many rows, error/loading/success states, live authorized staging auth, and operational flows; the baseline fixture matrix alone cannot establish these.

# NextVN staging verification checklist

Date: 2026-10-15 (Asia/Saigon). All checks below are **NOT TESTED**. No isolated staging environment or test accounts are configured in this repository, and no production database mutation was performed.

Before starting, confirm a staging frontend and API with a separate, disposable database; record the deployment build ID, API origin, and test business/branch IDs in a private test log. Use dedicated Owner, Manager, and Staff accounts. Establish expected stock, open shifts, orders, alerts, and analytics totals through normal application setup or approved staging fixtures. Never run database reset, migration, seed, or destructive cleanup against production. Capture request IDs and redacted UI/API evidence; do not put credentials, tokens, customer data, or connection strings in this checklist.

| Priority | Workflow and safe staging steps                                                                                                                                                          | Expected result / evidence                                                                                                                                                                                               | Status         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------- |
| 1        | Log in separately as Owner, Manager, and Staff; reload a protected deep link; log out and revisit it.                                                                                    | Correct role landing and navigation, persisted authorized session, logout clears access, unauthenticated deep link returns to login. Record redacted role and route screenshots.                                         | **NOT TESTED** |
| 2        | For each role, try permitted and forbidden direct URLs and API reads across two test branches/businesses. Change branch only through a supported control, if one is provided in staging. | Server rejects unauthorized role and cross-branch access; visible business/branch matches the verified workspace. | 3        | Open a Staff shift, build an order with quantity/modifiers and a payment method, assign an eligible table where applicable, and check out once.                                          | One order and one payment state, correct cart total/payload, stable success feedback, correct table and shift association. | 4        | With known recipe quantities and opening stock in staging, check out one paid order and compare ingredient balances, lots, and transaction history.                                      | Each ingredient decreases by the recipe amount exactly once; no deduction for canceled/unpaid paths.                                                                                                                     | **NOT TESTED** |
| 5        | Retry a checkout or replay the same idempotency key under controlled staging conditions.                                                                                                 | Exactly one order/stock consumption for the logical transaction; duplicate response follows the backend contract. | 6        | Prepare stock below recipe demand and attempt a sale/adjustment according to supported rules.                                                                                            | Clear insufficient-stock response, no partial inventory write, consistent cart/order state, and no duplicate mutation on retry.                                                                                          | **NOT TESTED** |
| 7        | Bring a staging ingredient below minimum and another near expiry, then resolve/reopen an alert through Manager controls.                                                                 | Correct severity, status, counts, and timestamps in Manager and Owner views after refresh.                                                                                                                               | **NOT TESTED** |
| 8        | Compare Owner revenue, order count, average order value, menu profit, branch totals, and date filters with the staging order ledger.                                                     | Charts and currency values reconcile with documented backend calculations; no invented metrics.                                                                                                                          | **NOT TESTED** |

Additional regression passes: create/edit/suspend a branch; invite a member and change permitted role/branch; verify a Staff user cannot perform Owner actions; test failed API responses and retries; inspect responsive long-data tables, populated charts, dialogs, focus restoration, and a screen reader on supported browsers. Keep subscription payment disabled or use a provider sandbox only after a dedicated payment test plan. Record PASS/FAIL and evidence for each substep before a release decision.

Production readiness remains **BLOCKED** until the critical real API checks above pass in isolated staging, the frontend is built with the intended HTTPS API URL, and the root automated-check failure is resolved or explicitly accepted by release owners.
